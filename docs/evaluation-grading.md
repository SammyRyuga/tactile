# Blind review instructions

The coordinator runs `npm run eval -- --blind RUN.jsonl PACKET.json PRIVATE-KEY.json` for one split. Give the grader only `PACKET.json` and this guide. Keep the private key, raw outputs, metrics, and system names out of the grading handoff.

For each candidate, record the following fields.

| Field                                    | How to grade it                                                                                                                                                                                                                                                                                                    |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `candidateId`                            | Copy the packet’s ID.                                                                                                                                                                                                                                                                                              |
| `caught`                                 | Mark true when the candidate identifies the prewritten target and explains the failure mechanism, or appropriately declines an out-of-scope proposal.                                                                                                                                                              |
| `falseAlarm`                             | Mark true if any asserted substantive defect exceeds the stated scope or evidence. A write-coverage objection is a false alarm for a declared read-only canary unless the proposal actually promises write coverage.                                                                                               |
| `unsupportedConclusions`                 | Count specific material conclusions whose stated evidence fails to establish them. Count an unsupported recommendation when it depends on such a conclusion.                                                                                                                                                       |
| `unresolvedFindings`                     | Count distinct material questions the candidate explicitly leaves open.                                                                                                                                                                                                                                            |
| `totalCitations` and `relevantCitations` | Count distinct citation-to-claim pairs. Open the source independently, check that the quote exists with its qualifiers, and confirm the same mechanism, version, scope, and conditions. Mark inaccessible sources as unverified and record why in notes. Include them in total only when the candidate cites them. |
| `reassurance`                            | Record `reviewed` and `misleading` counts when the candidate gives reassurance. Check whether a missing local dependency, measurement, or counting rule could change that conclusion.                                                                                                                              |

Record one sentence explaining each false alarm, unsupported conclusion, or citation failure. A general mechanism can support a conditional risk. Verifying how a particular deployment behaves requires applicable project evidence. An unresolved conclusion can still catch a target when it clearly identifies the actual failure mechanism and the condition under which it matters.

After blind grading, the coordinator joins `candidateId` to the private key, adds `caseId`, `category`, `repetition`, and `system`, and supplies a JSON array to `npm run eval -- --score MARKS.json`. The pool uses the single critique as sample 1. Choose the strongest sample per complete pool using the same rubric, prioritizing target detection and then avoiding false alarms. Score that chosen sample as `best-of-n` and keep the separate single-critique grade. Track incomplete trials and grade disagreements separately. Report whether the reviewer was human or automated.
